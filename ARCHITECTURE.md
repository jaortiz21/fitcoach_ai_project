# Architecture Review

This is a high-level look at where FitCoach stands architecturally, written after fixing a couple of active bugs (see git log on `dev`). It's organized from most to least urgent.

## Memory is SQLite only — Qdrant is provisioned but unused

`docker-compose.yml` stands up a Qdrant container, the API image installs `qdrant-client`, and the README describes long-term memory in vector-search terms ("stores embeddings for long-term memory," "similar past context is retrieved"). None of that is actually true of the code: `app.py` never imports or calls the Qdrant client, and there's no embedding step anywhere. What actually exists is a SQLite-backed system of raw messages, LLM-generated summaries, and a small structured profile table (goals/constraints/preferences), which is a perfectly reasonable memory design on its own — but it's a different design than the one described, and it's running a whole extra container for nothing. Worth picking one path deliberately: either wire up real embedding-based retrieval against Qdrant for cases the structured profile can't capture (e.g., "what did I say about my knee three weeks ago" style recall), or drop Qdrant from the compose file and the Terraform plan and update the README to describe the system as it actually works. Right now it's paying the operational cost of a vector database with none of the benefit.

## No auth, and conversation_id is a bearer secret

Anyone who knows or guesses a `conversation_id` can read and write that conversation's full history and profile — there's no user account, token, or ownership check anywhere in `app.py`. That's a fine tradeoff for a single-user homelab tool, but it stops being fine the moment this is meant to "serve any consumer like any other LLM service," which is the explicit goal for the frontend. Before opening this up beyond your own network, it needs some notion of an authenticated user (even something lightweight like an API key or signed session cookie) with `conversation_id`s scoped to that user rather than being globally guessable strings. This also affects the frontend: right now it has to invent and remember a `conversation_id` client-side with no server-side ownership check backing it up.

## The AWS deployment target and the local stack have drifted apart

`Infrastructure/` defines ECS Fargate services for `api` and a `model` container, backed by EFS, ALB, and IAM — but it only covers two of the three services in `docker-compose.yml`; there's no Qdrant task definition at all, so a "production" deploy would be missing a service the local stack has. Separately, the API's ECS task mounts EFS at `/app/storage`, but the API's actual data path is `/app/data` (`DB_PATH` defaults to `data/conversations.db`, resolved relative to the container's `/app` workdir) — so as configured, the SQLite database on ECS would land on the container's ephemeral filesystem instead of the persistent EFS volume, and every redeploy would silently wipe conversation history. Also worth a second look: `container_port_api` defaults to `5000` and `container_port_model` defaults to `8000` in `variables.tf`, but the API actually listens on `8000` and the model container (built `FROM ollama/ollama`) listens on Ollama's default `11434` — the defaults as written don't match either service. None of this blocks local development, but it means the Terraform hasn't actually been exercised against how the containers really behave yet.

## No tests, no CI

There's no test suite and nothing enforcing that `main`/`dev` stay deployable — which is exactly how the `diff_profile` NameError (see the latest commit) sat unnoticed for six months: it only fires after 5 conversation turns trigger summarization, so casual testing wouldn't hit it. Even a thin smoke test — spin up the API against a stub Ollama response, hit `/chat` a few times past the summarization threshold, assert no 500s — would have caught both bugs fixed today. A GitHub Actions workflow running `python -m py_compile` plus that smoke test on every PR would be a low-effort, high-value addition given the infra to run one (ECR images, ECS) already exists.

## Everything is synchronous and single-writer

FastAPI runs non-`async def` route handlers in a thread pool, so the blocking `requests.post()` calls to Ollama aren't strictly wrong, but they do mean each in-flight chat request ties up a worker thread for the full duration of an LLM response (up to the 240s timeout). SQLite is also a single-writer database — fine at homelab scale, but worth knowing as a ceiling if "serve any consumer" means more than a handful of concurrent conversations. If this needs to scale past that, the natural next steps are an async HTTP client (`httpx`) for the Ollama calls and a move to Postgres (the README already gestures at this as the intended migration path).

## Miscellaneous gaps

Logging is entirely `print()` statements with no levels or structure, which makes this harder to operate once it's not just you tailing `docker logs` — worth swapping for Python's `logging` module with a couple of levels (INFO for lifecycle events, DEBUG for the per-message counters). There's also no way for a user to list, rename, or delete their own conversations — the API only supports creating and appending to them — which the new frontend works around with a client-side list in `localStorage`, but that's a workaround, not a real feature. And the model is hardcoded to a single `fitcoach` model per deployment; there's no per-request model selection, which is fine today but worth keeping in mind if you ever want to offer different coaching "personalities" or let power users pick a different base model.
